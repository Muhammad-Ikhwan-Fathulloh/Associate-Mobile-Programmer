Modul 7: API Lanjutan

Tujuan Pembelajaran

  1. Menyelesaikan CRUD lewat API dengan token
  2. Menyimpan token dengan aman
  3. Menyinkronkan data lokal dengan server (offline-first)
  4. Menjelaskan jaringan seluler dan ancaman komunikasi nirkabel

Materi: docs/hari-2/07-api-lanjutan-sinkronisasi.md

Sesi ini menyelesaikan jalur data: dari SQLite ke server dan kembali. Kita melengkapi API dengan login dan token, menyimpan token dengan aman, lalu membangun sinkronisasi offline-first. Sepanjang jalan kita membahas jaringan seluler dan ancaman komunikasi nirkabel, karena sinkronisasi berjalan di atas jaringan yang tidak selalu aman. Pesannya: data lokal dulu, kirim saat bisa, dan amankan jalurnya.

Konsep · simulasi: tekan S

Alur sinkronisasi

  • Simpan ke SQLite dulu (**offline-first**) dengan status PENDING.
  • Saat online: kirim semua PENDING (POST bila baru, PUT bila sudah punya serverId).
  • Tandai SYNCED dan simpan serverId dari server, lalu ambil data baru dari server.
  • Satu kegagalan tidak boleh menghentikan yang lain. Hasil dilaporkan: terkirim, diterima, gagal.
Buka simulasi offline-first. Buat beberapa catatan saat offline, lalu sambungkan jaringan. Minta peserta menjelaskan apa yang berubah pada status tiap catatan. Tekankan bahwa kegagalan satu catatan tidak boleh menghentikan yang lain.

Kode di Aplikasi

Kode sinkronisasi

Dua tahap: kirim yang tertunda, lalu ambil dari server. Pengujiannya memakai API palsu tanpa jaringan.

src/services/sync.ts

export async function sinkronkan(db: Penyimpanan, api: ApiClient, token: string): Promise<HasilSinkron> {
  const hasil: HasilSinkron = { terkirim: 0, diterima: 0, gagal: 0 };

  for (const n of await db.catatanPending()) {
    try {
      const di = n.serverId != null ? await api.ubahCatatan(token, n.serverId, n) : await api.buatCatatan(token, n);
      await db.tandaiSynced(n.id!, di.id);
      hasil.terkirim++;
    } catch {
      hasil.gagal++;
    }
  }

// ... selengkapnya di berkas ini
Telusuri dua tahap di sync.ts: kirim yang PENDING, lalu ambil dari server. Tunjukkan percabangan POST untuk catatan baru dan PUT untuk catatan yang sudah punya serverId. Sebut bahwa pengujiannya memakai API palsu sehingga tidak butuh jaringan.

Handover dan Mobile IP

  • **Handover**: sambungan berpindah ke menara lain saat pengguna bergerak.
  • **Mobile IP**: perangkat tetap dapat dijangkau dengan alamat yang sama saat berpindah jaringan.
  • Komponen GSM: MS (ponsel dan SIM), BTS (menara), BSC, MSC, serta HLR dan VLR (basis data pelanggan).
Buka simulasi handover dan lihat sambungan berpindah antar menara. Jelaskan Mobile IP sebagai cara perangkat tetap dapat dijangkau dengan alamat yang sama saat berpindah jaringan, dengan peran home agent dan foreign agent.

export function periksaUrlAman(url: string, izinkanLokal = false): string | null {
  let u: URL;
  try {
    u = new URL(url.trim());
  } catch {
    return 'URL tidak valid.';

Prinsip pengamanan aplikasi

  • Selalu **HTTPS** di produksi. HTTP hanya untuk server lokal saat pengembangan.
  • Rahasia di **secure store**, bukan di SQLite atau teks biasa.
  • **Validasi masukan** di aplikasi dan di server.
  • Jangan menaruh kunci rahasia di dalam kode aplikasi.
  • Minta **izin seperlunya** dan jelaskan alasannya.
Rangkum dengan lima prinsip yang bisa dicek di kode: selalu HTTPS, rahasia di secure store, validasi masukan, jangan taruh kunci rahasia di dalam aplikasi, dan minta izin seperlunya. Buka simulasi autentikasi: login untuk mendapat token, lalu coba endpoint dengan dan tanpa token. Diskusikan mengapa token itu harus disimpan di secure store.

Proyek Modul 7 · 90 menit

Sinkronisasi Offline-First

Lengkapi aplikasi catatan agar bekerja tanpa internet. Catatan disimpan lokal dengan status PENDING, lalu dikirim ke server saat pengguna menekan Sinkronkan. Token disimpan dengan aman.

  • Kolom sync_status (PENDING atau SYNCED) dan server_id pada tabel lokal.
  • Fungsi sinkronisasi: kirim PENDING (POST bila baru, PUT bila sudah punya server_id), tandai SYNCED, lalu ambil data baru dari server.
  • Satu kegagalan tidak menghentikan catatan lain; hasil dilaporkan (terkirim, diterima, gagal).
  • Token login disimpan di penyimpanan aman, bukan SQLite.
  • Alamat HTTP publik ditolak. HTTP hanya diizinkan ke alamat lokal untuk pengembangan.
  • Minimal 4 tes sinkronisasi dengan basis data tiruan dan API palsu.
